# Platform-application layer audit: lifecycle, dispatcher, animation, theme, fonts, a11y, localization, hot reload

Scope: `src/Linux.SailfishOS` on branch `feature/fixes` vs .NET MAUI 11.0.0-rc.1.26451.6, plain `lib/net11.0` build of
Microsoft.Maui / Microsoft.Maui.Controls / Microsoft.Maui.Essentials (the build this backend consumes). Android and
iOS references were decompiled from `lib/net11.0-android37.0` and `lib/net11.0-ios26.5` of the same packages (present
in `~/.nuget`). Static analysis only; nothing was built, deployed or run. Line numbers are from the working tree on
2026-10-04; decompile line numbers refer to `ilspycmd -t <Type>` output.

## Summary

- **Window lifecycle is a subset of Android/iOS.** `Created`, `Activated`, `Deactivated`, `Resumed` and `Stopped` are
  raised; `Destroying` and `Backgrounding(IPersistedState)` are never raised (no call site in `src/`). `Stopped` is raised
  only on `Qt.ApplicationSuspended` (`ActivationGate.cs:70-71`), which the docs themselves describe as "about to be
  killed"; minimizing to the cover is `Inactive` and raises only `Deactivated`. Consequence: `Application.OnSleep` does
  not run when the app goes to the cover, but `Application.OnResume` *does* run when it comes back (`Resumed` on 2→4,
  `ActivationGate.cs:68-69`). This is the biggest semantic deviation in the area and the template/docs claim parity
  (`docs/add-sailfish-to-existing-app.md:110`).
- **Quit path:** `OnQuitting`/`SailfishLifecycle.OnQuitting` fire from the shim's `svc-app-quit` (sent in teardown
  before callbacks are cleared, `host_core.cpp:1070`), but neither `IWindow.Stopped()` nor `IWindow.Destroying()` is
  sent, so `OnSleep`, `Window.Destroying`, `AlertManager.Unsubscribe`, `Application.RemoveWindow` and the window
  handler's `DisconnectHandler` never run on exit. No state persistence exists (`ActivationState(context)` always
  carries an empty `PersistedState`).
- **Dispatcher/MainThread are sound.** `SailfishDispatcher` meets `IDispatcher` semantics; `GetForCurrentThread()` is
  null off the loop thread like Android's Looper-less threads; `SailfishMainThread.Install` reaches the real internal
  `MainThread.SetCustomImplementation(Func<bool>, Action<Action>)`, which exists in the plain-net Essentials build
  (without it `MainThread.IsMainThread` throws `NotSupportedOrImplementedException`). Only cosmetic issues: a
  "Replaced an existing DispatcherProvider" warning MAUI logs because two `SailfishDispatcherProvider` instances exist,
  and a timer whose `Tick` throws re-fires every pump tick.
- **Theme flow is complete but starts Unspecified.** Ambience → `SailfishTheme.Apply` → `IApplication.ThemeChanged()`
  → `PlatformAppTheme = AppInfo.RequestedTheme` → `RequestedThemeChanged` + the `__MAUI_ApplicationTheme__` dynamic
  resource, so `AppThemeBinding` re-evaluates. But `Application`'s constructor snapshots `AppInfo.RequestedTheme` while
  `SailfishTheme.Current` is still `Unspecified` (the theme service starts on the first Qt tick), so the first page is
  built with `AppThemeBinding.Light` values and re-themed one tick later. `Application.AccentColor` is MAUI's hard-coded
  `#324F85` on plain-net; Silica's `Theme.highlightColor` is not exposed through any MAUI-visible API.
- **Loaded on plain-net Controls is `Window != null`** (`VisualElement.IsLoaded => Window != null`); there is no
  platform hook. The overlay's `CreatePage` comment is correct. A `Loaded` handler calling `Handler.PlatformView`
  (e.g. `SetSemanticFocus()`, which throws `NullReferenceException` on a null handler in plain-net) fails for every
  page the app constructs itself. The only pre-Loaded hook is `ParentChanging` on an already-known instance; the
  realistic fix is upstream (`IsLoaded => Window != null && IsPlatformEnabled`, since `OnHandlerChangedCore` already
  re-runs the wiring).
- **Back button bypasses MAUI's veto chain.** Hardware Back/Escape goes to `renderer.TryPop()` which calls
  `Navigation.PopAsync()`/`PopModalAsync()` directly; `Page.SendBackButtonPressed`, `Shell.OnBackButtonPressed`
  (`BackButtonBehavior.Command`) and `NavigationPage.OnBackButtonPressed` are never consulted (no occurrence in
  `src/`). Android routes Back through `IWindow.BackButtonClicked()`. The Silica swipe-back pops natively and MAUI
  follows (`FollowNative`), so an app cannot veto it.
- **Soft input:** plain-net `SoftInputExtensions.Hide/Show/IsSoftInputShowing` throw `NotSupportedException` once a
  platform view exists; the backend provides no replacement. The Maliit keyboard rectangle reaches only
  `OnInputMethodChanged`; nothing resizes or scrolls MAUI layout.
- **Fonts/a11y/localization:** `IFontManager` on plain-net has a single member (`DefaultFontSize`), so the 18 dp
  sentinel is the whole contract; embedded fonts are extracted and registered with Qt; `FontAutoScalingEnabled` is not
  consumed. `SemanticScreenReader.Announce` is a logged no-op (Sailfish has no screen reader); `SetSemanticFocus` is
  a no-op when a handler exists. `AppInfo.RequestedLayoutDirection` is hard-coded `LeftToRight`, so RTL system
  locales get LTR layouts unless the app sets `FlowDirection`. ICU mode is the default (no `InvariantGlobalization`
  in the template; SFOS 5.2 ships ICU 73 per `docs/aot-and-trimming.md:124`).
- **Crash policy is a deliberate, documented deviation**: dispatched/posted/Qt-callback exceptions are logged and the
  loop continues (`docs/porting-existing-apps.md:231-233`). **Hot reload:** nothing in `src/` or `tools/`; parity plan
  lists it as a gated VS Code extension item.
