# Build/SDK integration audit: maui-sailfish (feature/fixes) vs .NET MAUI 11 RC1 / .NET SDK 11.0.100-rc.1

Static analysis only. Reference material: SDK `~/Library/Application Support/dotnet/sdk/11.0.100-rc.1.26425.128`, MAUI packs/packages `11.0.0-rc.1.26451.6`, the official `maui` template from `template-packs/microsoft.maui.templates.net11.11.0.0-rc.1.26451.6.nupkg` (extracted to the scratchpad). Repo paths are relative to `/Users/mer/Projects/maui-sailfish`. `targets` = `src/Linux.SailfishOS/buildTransitive/Microsoft.Maui.SailfishOS.targets` (717 lines).

## Summary

1. **NuGet reserved prefix blocks every package id.** All five shipping ids start with `Microsoft.Maui.`: `Microsoft.Maui.SailfishOS` (`src/Linux.SailfishOS/Linux.SailfishOS.csproj:7`), `Microsoft.Maui.SailfishOS.SkiaSharp` (`src/Linux.SailfishOS.SkiaSharp/Linux.SailfishOS.SkiaSharp.csproj:10`), `Microsoft.Maui.SailfishOS.Workload` (`src/Linux.SailfishOS.Workload/Linux.SailfishOS.Workload.csproj:15`), `microsoft.maui.sailfishos.Manifest-11.0.100-rc.1` (`src/Linux.SailfishOS.WorkloadManifest/Linux.SailfishOS.WorkloadManifest.csproj:11`), `Microsoft.Maui.Platforms.SailfishOS.Templates` (`templates/sailfishos/SailfishOS.Templates.csproj:5`). `Microsoft.*` is a reserved prefix on nuget.org; a push from a non-Microsoft account is rejected. README.md:47 confirms nothing is published yet. Fix: rename ids (e.g. `Sailfish.Maui`, `Sailfish.Maui.SkiaSharp`, `Sailfish.Maui.Workload`, `sailfish.maui.Manifest-<band>`, `Sailfish.Maui.Templates`); the C# namespace/assembly name can stay but is misleading; `docs/add-sailfish-to-existing-app.md`, README, template.json and `tools/cmd/pack-local.sh:37-42,53,60` all hard-code the ids.
2. **TFM design relies on a manifest-on-disk plus clearing `TargetPlatformIdentifier` before `ProcessFrameworkReferences`** (`targets:194-199`). The clear is what makes MAUI's neutral-TFM backend hook fire (`MauiPlatformSpecificFolder` branch C requires an empty TPI, `Microsoft.Maui.Controls.SingleProject.targets:69-76,85`), but it also suppresses everything else keyed on TPI late in the build: no `[TargetPlatform]`/`[SupportedOSPlatform("sailfish1.0")]` assembly attributes (`Microsoft.NET.GenerateAssemblyInfo.targets:132-155`), no `SAILFISH`/`SAILFISH1_0`/`SAILFISH1_0_OR_GREATER` implicit defines (`Microsoft.NET.Sdk.BeforeCommon.targets:215-223,257-268`; the repo re-adds only `SAILFISH` at `targets:60`), and the platform-compat analyzer treats the head as cross-platform (CA1416 noise that `docs/add-sailfish-to-existing-app.md:188-189` reports).
3. **The in-box precedent (Tizen) is a whitelisted third-party manifest, not an SDK platform list.** The SDK has no hardcoded `tizen` in its targets; it knows the manifest id through `sdk/11.0.100-rc.1.26425.128/KnownWorkloadManifests.txt` (`samsung.net.sdk.tizen`, last line) and Samsung ships its own installer script, i.e. the same shape as `sailfish-workload`. `microsoft.maui.sailfishos` is not in that list, so `dotnet workload install sailfish` on a clean machine fails until the tool has copied the manifest (documented, decided option (a)). The manifest declares one pack of kind `library` and no `sdk`/`framework`/`template` packs (`data/WorkloadManifest.json.in:11-16`).
4. **Resizetizer is driven through a private side door.** MAUI 11 RC1 has an explicit external-backend contract: set `ResizetizerPlatformType` and the package wires `_PrepareExternalMauiImages/_PrepareExternalMauiAssets/_PrepareExternalMauiFonts` and `ResizetizerAfterAssetProcessingTargets` (`Microsoft.Maui.Resizetizer.After.targets:138-141,414-433,476-478`). The repo instead calls the `ResizetizeImages` task itself with `PlatformType="wpf"` (`targets:148-183`), copies `MauiFont` raw (`targets:130`) and resolves `MauiAsset` itself (`targets:136-146`). The task's `PlatformType` enum has only `Android`, `Ios`, `Tizen`, `Wpf` (strings in `Microsoft.Maui.Resizetizer.dll`); there is no generic value, so even the official hook would need `wpf`. `MauiSplashScreen` is ignored (decided).
5. **Trimming profile matches MAUI's mobile defaults; the backend itself is not trimmed.** Release = `PublishTrimmed` + `TrimMode=partial` + `PublishReadyToRun` (`targets:281-294`). Android defaults to `partial` whenever `PublishTrimmed=true` (`Microsoft.Android.Sdk.DefaultProperties.targets:107-111`), iOS `SdkOnly -> partial` (`Xamarin.Shared.Sdk.Trimming.props:86`); the plain SDK default would be `full` (`microsoft.net.illink.tasks/11.0.0-rc.1.26425.128/build/Microsoft.NET.ILLink.targets:215`). `Microsoft.Maui.SailfishOS.dll` carries no `IsTrimmable` metadata (MAUI's dlls do), so under `partial` the backend and the app are copied untrimmed; the wildcard `scaffold/trimmer.xml` root (`*MauiProgram`) only matters under `TrimMode=full`. No MAUI feature switch is set by the repo; `MetricsSupport=false` in Release (`targets:310`) and `SatelliteResourceLanguages=en` only when the app opts into `InvariantGlobalization` (`targets:320-322`) are the only runtime knobs.
6. **Package layout quirks.** 26 shell/python tool files ship under `buildTransitive/net11.0/tools` (unusual for a MAUI platform package; `Linux.SailfishOS.csproj:50-64`), the Harbour launcher lands at `runtimes/linux-arm64/native/sailfish-launcher/sailfish-launcher` because an extension-less `PackagePath` is read as a folder (`Linux.SailfishOS.csproj:73`; confirmed in the cached nupkg and `samples/SailfishKitchen/obj/project.assets.json:2763`) and only works because the SDK flattens native assets by file name, no `snupkg`/`IncludeSymbols`, version pinned at 0.1.0 (`Directory.Build.props:15`).
7. **Tests cover the managed renderer well, the build system not at all.** 326 `[Fact]/[Theory]` attributes (+80 `InlineData`) across 41 files; the 717-line targets file, the workload manifest targets, the template and the RPM pipeline have no host test (only `ToolsPackagingTests` checks the tools pack list). QML (43 files, 6.8k LOC) is covered only by key/contract checks, the C++ shim (4.2k LOC) only by text-based `NativeContractTests`. No `.github/` CI, no `.editorconfig`, no analyzers/`TreatWarningsAsErrors` outside `tests/Linux.SailfishOS.PublicApiGuard`.
8. **DX gaps vs an in-box head:** debugging is VS Code-only via vsdbg over an SSH pipe (works), MAUI 11's XAML incremental hot reload is on in Debug (`Microsoft.Maui.Controls.targets:19-24`) but has no agent/IDE path for the phone, `dotnet watch` untested (`docs/parity-plan.md:260`), MAUI 11 RC1 ships no device `dotnet test` runner (no `Microsoft.Testing.Platform`/test hooks in the Controls.Build.Tasks, Maui.Sdk, Android or iOS packs), so `dotnet test -f net11.0-sailfish` is not feasible without a custom runner; the matrix (31 legs, `tools/cmd/matrix.sh:22`) is the substitute.
9. **Template is a faithful copy of the official `maui` template's non-sample variant** (`CreateWindow`, Shell, same Platforms files modulo namespace), minus the official symbols (`IncludeSampleContent`, `WithAvalonia`, `Framework`, `applicationId`, `skipRestore`, localized strings, `$guid9$` PhoneProductId: the Sailfish copy ships a fixed GUID at `templates/maui-sailfish-app/Platforms/Windows/Package.appxmanifest:11`).
